# sync/

Background sync + notification scheduling for `openMF/kmp-project-template`, powered by [worker-kmp](https://github.com/MobileByteLabs/worker-kmp).

This module is the **integration layer** between the template's `core/data` + `core/datastore` modules and worker-kmp's cross-platform `WorkManager`. Consumer feature modules (`feature/loans`, `feature/bills`, …) depend on this module only via a single Koin-injectable interface — [`WorkScheduler`](src/commonMain/kotlin/kpt/sync/WorkScheduler.kt) — and never see `io.github.mobilebytelabs.worker.*` types directly.

## What ships

| Surface | File | Purpose |
|---------|------|---------|
| `WorkScheduler` interface | `WorkScheduler.kt` | The cross-module API. 4 methods: `enqueueDataSync`, `scheduleNotification`, `observeWork`, `cancelWork`. |
| `DefaultWorkScheduler` impl | `DefaultWorkScheduler.kt` | Thin façade over worker-kmp's `WorkManager`. Encodes KEEP unique-name policy for data sync + expedited-on-Foreground mode mapping. |
| `DataSyncWorker` | `DataSyncWorker.kt` | `CoroutineWorker` + `Synchronizer`. Fans out to `currencyRepository.syncWith(this)` + `macroIndicatorsRepository.syncWith(this)` in parallel via explicit `awaitAll` — **no `getAll<Syncable>()` runtime discovery**. |
| `NotificationWorker` | `NotificationWorker.kt` | `CoroutineWorker` that renders a notification via the per-platform `renderNotification` expect/actual (Android real; other platforms log-and-return via the shared `nonAndroidMain` actual). |
| `SyncModule` (Koin) | `di/SyncModule.kt` | Binds `WorkScheduler` only. Sync-status observation is provided by the `cmp-worker-sync` library's `UniqueWorkObserver` (bound via `SyncObserverKoinModule`), which replaced the hand-rolled per-platform `SyncManager` expect/actuals in the worker-kmp v4.0.0 single-API migration. |

## Sync flow (Android)

```
{platform}App entry (Android onCreate / Desktop main / Web main / iOS ViewController)
  → initKoin { … }                                 // commonMain — cmp-shared/utils/KoinExt.kt
      → startKoin { config?.invoke(this); modules(allModules + SyncModule) }
      → WorkerKmpAuto.install()                     // ← ONE commonMain call, EVERY platform.
                                                    //   generated by @WorkerKmpWorkers (v4.0 single-API):
                                                    //   builds the workerRegistry from DataSyncWorker +
                                                    //   NotificationWorker, loads the work Koin module,
                                                    //   initializes WorkerKmpHost. Replaces the old
                                                    //   loadKoinModules(workKoinModule(...)) block.
                                                    //   (Android reads the Application from the
                                                    //    androidContext bound in `config`.)
  → get<WorkScheduler>().enqueueDataSync(mode = WorkMode.Background)   // first-launch data sync
      → workManager.enqueueUniqueWork(DATA_SYNC_WORK_NAME, KEEP, OneTimeWorkRequest<DataSyncWorker>)
        → DataSyncWorker.doWork()
          → workingVersions = persister.read()                                              // SyncStatePersister (Settings)
          → coroutineScope {
                async { currencyRepository.syncWith(this@DataSyncWorker) }
                async { macroIndicatorsRepository.syncWith(this@DataSyncWorker) }
            }.awaitAll().all { it }
              → CurrencyRepositoryImpl.syncWith → snapshotSync("currency-rates") {
                    awaitAll(PINNED_BASE_CURRENCIES.map { async {
                        exchangeRatesStore.stream(StoreReadRequest.fresh(it))
                            .first { it is StoreReadResponse.Data<*> || it is StoreReadResponse.Error }
                    } })
                }
              → MacroIndicatorsRepositoryImpl.syncWith → snapshotSync("macro-indicators") {
                    awaitAll(PINNED_MACRO_KEYS.map { async {
                        macroIndicatorStore.stream(StoreReadRequest.fresh(it))
                            .first { it is StoreReadResponse.Data<*> || it is StoreReadResponse.Error }
                    } })
                }
          → persister.write(workingVersions)                                                // commits new snapshot timestamps
          → WorkResult.success()
```

UI observers see the sync state via the injected `WorkScheduler.observeWork(handle)` flow (or the
`cmp-worker-sync` `UniqueWorkObserver`), mapped to a Boolean for a top-bar spinner:
```kotlin
LaunchedEffect(Unit) {
    workScheduler.observeWork(handle).collect { status -> /* render spinner while Running */ }
}
```

## The forced-refresh seam

The two `Syncable` adopters force the underlying Store5 cache to re-fetch from network via Store5's
one-shot **`store.stream(StoreReadRequest.fresh(key))`**, collecting the first terminal
(`StoreReadResponse.Data` / `.Error`) emission. `fresh` bypasses the cache, hits the network fetcher,
and writes through `SourceOfTruth` automatically. A cold `stream(fresh)` **completes** on that first
terminal response, so the worker returns promptly.

> **Why not `asScreenStream(NETWORK_ONLY)` or `Store.fresh(key)`?** `asScreenStream(scope, …)` launches
> perpetual auto-refresh / network-monitor coroutines into its `scope` (it is built for long-lived UI
> subscriptions), so a `syncWith` built on it never terminates and the worker hangs. And store5-5.1.0-alpha08
> has **no** public `Store.fresh(key)` / `Store.write()` extension. `stream(StoreReadRequest.fresh(key))`
> is the canonical one-shot forced read (the same primitive `StorePagingSource` uses) and is the only
> shape that both refreshes AND completes.

This is the deliberate design choice: the integration ships **zero
edits to `core-base/store/**`** because the seam needed already exists at the Store5 library level. The
repo simply issues a `fresh` stream read per pinned input from the read side.

## How to add a third `Syncable` adopter

1. Declare `: Syncable` on the target repository interface (e.g. `FredInterestRatesRepository : Syncable`).
2. Implement `override suspend fun syncWith(synchronizer: Synchronizer): Boolean` in the impl, calling `synchronizer.snapshotSync(name = "…") { /* store.stream(StoreReadRequest.fresh(key)).first { terminal } per pinned input */ }`.
3. Add the repository as a constructor parameter to [`DataSyncWorker`](src/commonMain/kotlin/kpt/sync/DataSyncWorker.kt) and a third `async { repo.syncWith(this@DataSyncWorker) }` line in `doWork`.
4. Nothing else — the worker registry + Koin injection are **codegen'd** from the `@WorkerKmpWorkers` declaration in [`cmp-shared/WorkerDeclarations.kt`](../cmp-shared/src/commonMain/kotlin/cmp/shared/WorkerDeclarations.kt); the new constructor param is auto-wired via `getKoin().get()`. No hand-edited registry, no per-platform app-class change.

The explicit constructor surface is a deliberate trade-off — it adds friction for adding new Syncables but eliminates a class of runtime-discovery bugs and lets `DataSyncWorker.doWork()` be statically reasoned about. Three is the natural cap before refactoring to a registry pattern.

## Out of scope (v1)

- Real iOS / Desktop / Web background scheduling — worker execution on those platforms uses worker-kmp's default per-platform backing; only the Android path is exercised end-to-end at v1.
- Real Android notification rendering — `renderNotification` logs at INFO at v1 (follow-up: wire `NotificationManagerCompat` + a sync-related channel created at `App.onCreate`, optional `POST_NOTIFICATIONS` runtime permission on API 33+).
- Delta-sync algorithm callers (`changeListSync`) — the algorithm ships in `core/data/Synchronizer.kt` ready for the upstream Mifos Fineract PR conversation, but is unused at v1 because both pinned adopters (Frankfurter, World Bank) are snapshot APIs.
